### 2.5 排练站点和正式站点：二维码、平板、切换（2026-11-08 补）

**桌上二维码里是什么**（读 `self_ordering.py` 的 `generate_qr_token` / `_verify_qr_token`、`qr_print.py`）：一个网址 `<public_url>/order/?t=<令牌>`，令牌是 base64(`<Self Ordering Profile 的名字>|<桌子名>|<HMAC-SHA256(前两项, qr_signing_secret)>`)。**没有任何东西存在服务器的每张桌子上**（无状态）。所以二维码只依赖四样东西：① 网址里的域名；② Profile 的名字（现在是分店名 `三友寿司`）；③ 桌子名；④ Profile 的 `qr_signing_secret`。这四样在排练站点和正式站点上**一模一样**，二维码就两边都有效，贴一次就够。

**怎么保证一模一样：**
1. **签名密钥用一个约定的值**，不让每个站点自己随机生成（现在 Profile 保存时为空就自动随机生成）。12/1 定下这个值，存进密码管理器，数据包里带它；`deploy_check` 加一项：用样例令牌验证签名。
2. **域名**：二维码用正式域名（11/15 定）。试营业期间域名指向排练站点，切换（12/19）时指向正式站点，**贴出去的二维码不变**。
3. **Profile 名和桌子名在 11/27 冻结**，之后不再改（改了，对应的二维码全部作废，要重新打印）。**排进日历**：11/27 冻结，12/4 打印，12/9～12/11 贴。
4. **换密钥会让所有已贴二维码失效**（这也是紧急时的一个开关，比如二维码被人拍下乱传），要重新打印。

**平板：** 设备记录（`URY Ordering Device`）里存的是 `device_id` 和**凭据的哈希**，平板的 localStorage 里是原始凭据。数据包把设备记录（含哈希，不含原始凭据）一起带到正式站点，平板就**不用重新登记**。平板访问店里的固定局域网名字（`ury.lan`），切换时这个名字也指向正式站点。（要做：数据包里"导出 / 导入设备"。）

**切换站点：** 排练站点和正式站点在同一台服务器上，用同一套脚本建，数据包可重复执行（幂等）。切换 = 让域名和 `ury.lan` 从排练站点改指向正式站点（frappe_docker 里用 `FRAPPE_SITE_NAME_HEADER` 之类的单点设置，**具体机制 12/1～12/4 的部署演练里验证**，这里先当作一个已知风险）。正式站点在 12/10～12/11 就建好，期间不对外：没有开班记录，顾客扫码只会看到"未开放"，平板显示等待画面，所以不会产生单据。

**12/19 切换后的验证（不产生单据）：** 手机扫一张贴好的二维码 → 看到"未开放"；一台平板 → 等待画面；各角色账号能登录；厨房屏幕账号能登录；QZ 打印一张测试页（不是小票）；`deploy_check` 结果为空；备份能跑；Error Log 干净。**12/20 开班后的第一单是真正的第一单**。

**数据包脚本里显式设置站点语言、时区、国家（2026-11-09 补）：** 站点用 `bench new-site` 建、再用数据包导入时**不会走设置向导**，System Settings 的语言会留在 `en`（开发站点和测试站点就是这样，`deploy_check` 的“站点设置”一项因此报 FAIL）；走向导则默认选「日本語」，向导会把 `language` 设成 `ja`。所以数据包导入脚本要**幂等地设置**：System Settings 的 `language = ja`、`time_zone = Asia/Tokyo`、`country = Japan`，Global Defaults 的 `default_currency = JPY`（和向导设的一致），导入后 `deploy_check` 照样检查。员工账号的语言也是在数据包里设成 `ja`（`deploy_check` 的“店员语言”一项警告）。

**数据包里不带的：** 单据（POS Invoice、KOT、订单号）、开班记录、会话；这些在正式站点上从零开始，账本是干净的。

**风险：** ① 切换机制没验证过（12/1 演练）；② 试营业中改了菜单或桌子，要在 12/18 再应用一次数据包（桌子名不许改，菜单价格可以改）；③ 排练站点和正式站点同时在一台服务器上，要看内存和磁盘够不够。

### 2.6 机密和店内网络（2026-11-08 补）

**二维码签名密钥 `qr_signing_secret`**
- 它决定哪些二维码有效；泄露后别人可以伪造任意桌子的二维码（下单到一张开着的桌子上）。
- **现在存在哪里**：数据库里 URY Self Ordering Profile 的 `qr_signing_secret` 字段（`Data`），**不在** `site_config.json`，所以它会出现在每份数据库备份里。**更正（2026-11-08，我原来写错了）**：这个字段从创建起就是 `hidden = 1`、`read_only = 1`，所以 **Desk 的表单里谁都看不到它（Administrator 也看不到）**；但"隐藏"只是界面设置，**接口照样返回**：修复前 Cashier、Manager、URY Admin、Self Ordering Manager 通过 `frappe.client.get` 或 `/api/resource/URY Self Ordering Profile/<名字>` 读得到。2026-11-08 已把字段改为权限级别 1（只有 System Manager 能读写），并用真实 HTTP 请求在开发站点验证：Cashier、Manager 得到的响应里没有这个键，Administrator 有。
- **System Manager 现在怎么查看和设置它**（字段在表单里是隐藏的，所以走命令行）：
  - 查看：`bench --site <站点> execute frappe.db.get_value --args '["URY Self Ordering Profile","<Profile 名>","qr_signing_secret"]'`
  - 设置：`bench --site <站点> execute frappe.db.set_value --args '["URY Self Ordering Profile","<Profile 名>","qr_signing_secret","<值>"]'`（`execute` 结束时会提交）。**值会出现在命令行和 shell 历史里**，设置完用 `history -d` 删掉那一行，或者在 `bench --site <站点> console` 里交互地输入（`import getpass; frappe.db.set_value(..., getpass.getpass())` 之后 `frappe.db.commit()`）。
  - **建议改进（等你定，开店前约 0.25 天）**：把字段改成**表单里可见、可编辑**（`hidden = 0`、`read_only = 0`），因为它已经是权限级别 1，只有 System Manager 看得见和改得了；这样店主在 Desk 里就能粘贴密码管理器里的值，不用命令行，也不会留在 shell 历史里。代价：System Manager 的屏幕上会显示它（共享屏幕时要注意）。也需要一次 DocType 改动和 migrate。
- **开发站点和测试站点现有的密钥值曾经对非 System Manager 可见**（Cashier、Manager、URY Admin、Self Ordering Manager 都读得到，直到 2026-11-08 的权限级别修复），视为**已泄露**。**排练站点和正式站点必须用新生成的值**，不能沿用开发站点的（也不要把测试站点的值当作"约定的值"）。已经用开发站点的值打印过的二维码（测试用的）开店前要全部作废，正式的二维码用新值打印。
- **约定的值不能写进 git 仓库或任何会提交的文件**（包括文档、测试、脚本里的默认值；测试里用的 `self-order-test-secret` 只是测试用的假值）。
- **怎么带到各个站点**：生成一次（48 位随机），存进**密码管理器**；数据包里**不含**它，由部署时在 Desk 里（System Manager）或用命令设置：`bench --site <站点> set-value`，每个站点各设一次，值相同。数据包文件本身按机密处理（里面有账号名单、设备凭据哈希）。
- **谁保管**：店主（你）一份；我不保留。部署演练时你把它给我在服务器上设置，或你自己设置。
- **密钥改成 Password 字段类型（2026-11-08 决定，和平板的下一次 DocType 改动一起 migrate）**：表单里显示成掩码，可以直接粘贴新值；值加密存在 `__Auth` 表里（用站点 `site_config.json` 里的 `encryption_key`），Profile 表里只留 `*****`；接口（`/api/resource`、`frappe.client.get`）只给掩码，共享屏幕也不会露出来。已有站点的明文值由补丁 `encrypt_qr_signing_secret` 迁移（先写 `__Auth`、再把表里的列清成 `*****`、可重复执行，**值不变，已贴的二维码继续有效**）。Desk 里**看不到现有值**，只能重新输入覆盖；要看明文用 `bench --site <站点> execute frappe.utils.password.get_decrypted_password --args '["URY Self Ordering Profile","<Profile 名>","qr_signing_secret"]'`，以密码管理器里的值为准。
- **备份要成套当机密保管**：`bench backup` 生成两个文件，数据库备份（`...-database.sql.gz`）和**配置备份（`...-site_config_backup.json`，里面有数据库密码和 `encryption_key`）**。只有数据库备份解不开密钥（里面是加密值），**有了成套的两个文件就能解开**。所以：两个文件一起存放、一起保护（放在加密的磁盘或加密的云存储里，不放在能被店员或顾客拿到的地方）；**谁能拿到**：只有店主和被明确授权的管理员；备份不要发给我，也不要放进 git。（数据库备份里原来就有顾客、订单和账号信息，本来就不该外传。）
- **还原到另一台服务器时必须带上原站点的 `encryption_key`**（在 `site_config.json` 里），否则所有加密字段（二维码密钥，以后的邮件账号密码等）都解不开。**12/8 的还原演练要实际验证**：在另一个站点上还原成套备份，确认能登录、签名密钥能解密、**已贴的二维码令牌验证仍然通过**（用样例令牌，`deploy_check` 的那一项）。排练站点和正式站点的 `encryption_key` 各不相同，所以**每个站点的密钥都要各自设置一次**，不能把 `__Auth` 的行拷来拷去（这和"数据包不含密钥"一致）。
- **泄露后怎么办**：换新值（所有站点同步换）；**所有桌上二维码要重新打印、重新贴**（旧的立刻失效）。所以平时就要少一个人知道。
- `deploy_check` 加一项：用样例令牌验证签名，两个站点用的密钥一致才通过（只比较签名结果，不输出密钥）。
- `deploy_check` 再加两项（见 `report-permissions.md`）：**只有 URY Manager、URY Admin、System Manager 对 URY Report Settings 有 `read`**（出现其他角色就列出来，因为这等于给了它全部报表权限）；**URY Captain、URY Cashier 在任何 DocType 上都没有 `export`**（按有效权限查，列出出现的 DocType）。

**店内网络（你做）**
1. **本地 DNS**：平板通过 `ury.lan` 找到服务器，要在店内路由器上做一条本地 DNS 记录（或 DHCP 的主机名映射）：`ury.lan` → 服务器的固定局域网 IP。很多家用路由器没有这个功能；替代：直接用固定 IP（`http://192.168.x.y`）当 Local URL（简单，但服务器换 IP 时所有平板要重新设置），或服务器上装一个小的本地 DNS（dnsmasq）。**请把路由器型号告诉我**，我给具体步骤。
2. **平板和顾客的 Wi-Fi 要隔离**：顾客用**访客 Wi-Fi**（和店内网络隔离，开启客户端隔离，只能上互联网），平板、收银电脑、打印机、服务器在**店内网络**。
   - 为什么：平板的凭据在局域网里走 **http**（明文）。同一网络上的人能抓到凭据，拿它冒充那台平板（能做的：在那张桌子**开着**的时候用它下单，和扫二维码差不多，进不了员工界面），更大的风险是顾客的手机能直接连到服务器（登录页、SSH、数据库端口）和打印机（9100 端口）。
   - **如果隔离做不到**（路由器不支持访客网络或 VLAN）：风险就是上面这些。替代方案：① **局域网也用 https**：用正式域名（如 `order.<域名>`），让店内路由器的 DNS 把它解析到服务器的内网 IP，用 Let's Encrypt 的 DNS 验证证书（通过 Cloudflare），平板就能用 https 且没有证书警告，凭据不再明文（设计 9 章 #7 已提到，需验证）；② 服务器防火墙只允许员工设备的 IP 访问管理类路径。这两项可以在部署演练（12/1～12/4）里一起验证。
3. 路由器不做端口转发（已有）。

### 2.7 更新正式站点的顺序（2026-11-08 补）

**起因**：2026-11-08 开发站点上，字段改名的代码先生效、数据库晚 6 小时才 migrate，这期间平板每次报到都出 `Unknown column 'last_reported_at'`，Error Log 里积累了 3359 条（05:45～11:28）。**代码比数据库新，每个碰到新列的请求都会报错**；正式环境营业中出现，等于点单、报到失败。

**更新顺序（营业时间外做，闭店后）：**
1. 确认没有进行中的订单、没有未交班的班次（或明确告知店员暂停）。
2. **备份**（`bench --site <站点> backup`，成套两个文件，当机密保管）。
3. **让站点不对外服务**：`bench --site <站点> set-maintenance-mode on`（请求得到维护页面，不会碰到新旧不一致的代码和结构）。
4. 部署新代码（新镜像 / 拉代码 + 构建前端），重启服务。**前端构建产物不在 git 里**（`.gitignore` 排除了 `ury/public/pos`、`ury/public/mosaic`、`ury/public/order`、`ury/public/ury`、`ury/public/urypos` 和对应的 `ury/www/*.html`），每次部署必须在目标环境生成：`bench build --app ury` 会执行仓库根 `package.json` 的 `build`（依次构建 mosaic、pos、frontend、self-order；self-order 的 base 是 `/assets/ury/order/`）。**用 frappe_docker 构建镜像时是否自动执行这一步、node 和 yarn 版本是否满足，我没有核实**，12/1～12/4 的部署演练里确认（做法：镜像里 `ls apps/ury/ury/public/order` 看有没有 `index.html` 和 `assets/`，没有就是没构建，顾客页面会是空白）。
5. `bench --site <站点> migrate`；完成后只读核对：Patch Log、新列、Error Log 条数没有增加。
6. `bench --site <站点> set-maintenance-mode off`；`deploy_check`；让所有平板刷新页面一次。
7. 更新前后各记一次 Error Log 总数。
8. **浏览器要强制刷新**（电脑上 `Ctrl` + `Shift` + `R`；平板下拉刷新）：Desk 的列表脚本（例如设备列表的 `_list.js`）会被浏览器缓存，2026-11-08 改名后设备列表一直显示红色，强制刷新后才变绿。更新后核对静态文件版本已变（`bench build` 之后页面请求的文件名 / hash 变了），否则界面还在用旧代码。

**frappe_docker 会不会自动保证这个顺序：我没有核实，不要当作会。** 我印象中它的生产配置只是换镜像、重启容器，`migrate` 要自己执行（官方的更新说明里是单独的一步），也没有自动开维护模式；**所以上面的顺序要手工做，写成一个脚本**。12/1～12/4 的部署演练里用演练站点实际做一次更新（包括带结构改动的版本），确认容器重启期间的行为后再写进部署步骤。

**开发站点的区别**：`bench serve` 自动加载新代码，数据库不会自动 migrate，所以改了 DocType 或补丁之后要尽快 migrate，不要让平板窗口一直开着。

### 3.2 iPad 的设置要求和步骤（店员照着做；3 台都要自己设置）

**买什么：** 当前在售、带 Wi-Fi 的 iPad（不需要蜂窝版），10 英寸左右，存储 64GB 足够；**iPadOS 17 以上**（要能升级到当前版本，保证 Safari 和安全更新）；配一个能固定在桌上的支架或保护壳（防掉落、防被拿走）。电池和充电见 3.3。

**设置步骤（日语界面；菜单名称随 iPadOS 版本可能略有不同，拿到第一台后我按实际画面核对修正）：**
1. **联网**：設定 > Wi-Fi，连接**店内网络**（不是访客 Wi-Fi），「自動接続」开；「プライベートWi-Fiアドレス」对这个网络设为「オフ」（固定 MAC，路由器上做 DHCP 预留时用）。
2. **自动锁定设为永不**：設定 > 画面表示と明るさ > 自動ロック > **なし**。亮度建议 **50% 左右**，「明るさの自動調節」开。
3. **关通知和打扰**：設定 > 通知，全部关闭（或开「おやすみモード」）；设置 > 一般 > ソフトウェアアップデート > 自動アップデート **关**（营业时间中不要自己更新重启），更新在闭店后手动做。
4. **设备设置**：在 Desk 的设备记录上点「発行（設定用 QR）」，用这台 iPad 的 Safari **打开链接**（或用相机扫二维码）。看到「設定が完了しました」后进入「ご注文の準備ができるまでお待ちください」（等待画面）。**这时页面地址是 `/order/?tablet=1`：在这个页面上点 Safari 的分享按钮 > 「ホーム画面に追加」，以后一律从主屏幕图标打开；不要用旧的收藏，也不要手输网址**（地址里的 `tablet=1` 是标记：Safari 清掉网站数据后，带标记的页面会显示「この端末は設定されていません」，而不是顾客的提示；手输或旧收藏没有这个标记）。
5. **引导式访问（アクセスガイド）**：設定 > アクセシビリティ > アクセスガイド > **オン**，「パスコード設定」设一个只有店员知道的密码，「アクセシビリティのショートカット」开。然后**从主屏幕图标**打开点餐页面（第 4 步加的那个；不要手输 `http://ury.lan/order/`，那样没有 `tablet=1`），**连按三次顶部（或 Home）按钮**，选「オプション」：「タッチ」开、「キーボード」关、「モーション」关、「スリープ/スリープ解除ボタン」关、「時間制限」关，点「開始」。之后客人只能在这个页面里操作，不能退出。退出：连按三次按钮，输入密码，点「終了」。
6. **测试**：在 POS 把这张桌子开启自助点餐，iPad 应在几秒内出现菜单；点一道菜（用测试桌，事后取消）；在 POS 关闭，应回到等待画面。

**要在第一台 iPad 上验证的（我没法提前确认）：**
- 引导式访问下 Safari 的地址栏和标签页是否仍然可见、能否被客人点到；如果可以，评估"添加到主屏幕"（做成全屏的网页应用，需要给页面加 `apple-mobile-web-app-capable` 和 manifest）。**注意**：主屏幕网页应用和 Safari 的本地存储**是分开的**，设备凭据要在哪一边保存、设置链接怎么打开，要一起验证，所以现在不改。
- **Safari 的存储清理**：Safari 对很久没有操作过的网站会清掉本地存储（我印象中约 7 天没使用 Safari 访问该站点就会清；**我没有在这台设备上核实**）。凭据存在本地存储里，被清掉后平板会变成"没设置"，需要重新用设置链接设置（约 3 分钟）。长假休店前要注意；**没设置的平板（地址带 `tablet=1`、没有凭据）会显示「この端末は設定されていません」+ `E-DEVICE-NOT-SET`（已做）；没有 `tablet=1` 的页面仍显示顾客用的「注文コードが見つかりません」，因为它和顾客手机无法区分。**

### 3.3 电池供电：评估和实测计划

- **耗电的主要来源是屏幕常亮**，不是我们的轮询：每 5 秒（等待时）或 20 秒（点餐时）一个很小的请求，只会让 Wi-Fi 比深度休眠多醒几次，量级远小于屏幕。Apple 对 iPad 公布的"网页浏览续航"一般在 10 小时左右（具体型号以官网为准，我没有核实你要买的型号，也是 50% 亮度的数字），而营业日如果有 10～12 小时，**不充电大概率撑不到闭店**。
- **实测方案（拿到 iPad 后，约 3 小时）：** 充满电，按 3.2 设置，亮度 50%：① 等待画面、轮询 5 秒，放 60 分钟，记电量下降；② 同样条件轮询 15 秒，60 分钟；③ 点餐画面（每 20 秒一次）60 分钟，期间每 10 分钟点几下；④ 亮度 30% 重复 ①。根据结果定充电方式和轮询间隔。
- **降低轮询（建议，实测后再改）：** 等待画面 5 秒 → **10 秒**（店员开桌到平板出现菜单最多多等 5 秒，可以接受），点餐中的心跳 20 秒 → **30 秒**（桌子关闭后最多 30 秒回到等待画面）。`device.ts` 里的 `pollDelay` 一处改，测试已覆盖范围。网页**不能**控制 iPad 的亮度，调暗只能靠设置里的亮度。iPad 是液晶屏，页面用深色背景省不了电。
- **充电方式（草案，实测后定）：** ① **闭店后**把 3 台放进多口 USB 充电座充满（每天）；② 营业日如果电量会低于 30%：**用备用机替换**（见 3.4），低电量的拿去充电；③ 桌边留充电线作为应急，不作为常态（线会碍事、也容易被客人拔掉）。写进店员操作说明（12/8 的培训材料）。

### 3.4 备用机和替换

- 3 台里 2 台固定在桌上，**1 台备用**。设备记录**按桌子建 2 个**（每张桌子一个，不为备用机单独建记录）。
- **替换一台没电或坏了的平板（约 3 分钟）：** Desk 打开那张桌子的设备记录 → 点「発行（設定用 QR）」（旧凭据立刻作废，坏的那台就算还在也进不了点餐）→ 用备用 iPad 的 Safari 打开链接 → 等待画面出现 → 连按三次按钮开启引导式访问。备用机平时已经按 3.2 的第 1～3 步设好，只缺凭据，所以只做 4、5 两步。
- **退役或更换平板：不要删除设备记录，用「停用」。** 设备一旦用过（有点餐会话引用它），系统不允许删除（`LinkExistsError`：You can disable this URY Ordering Device instead of deleting it），要删就得先删它的会话，而有订单的会话必须保留（订单指向它，是"谁下的单"的记录）。做法：在设备记录里取消勾选 **Enabled**。停用后这台平板马上进不了点餐；记录和会话留着，不影响账本。
- **换一台新平板（和上面的"替换没电的平板"不同：旧的不再用了）：**
  1. 新建设备记录（新的 Device ID，Table Mode 固定，Fixed Table 填那张桌子，Enabled 勾上）；
  2. 点「発行（設定用 QR）」，用新平板的 Safari 打开链接，看到等待画面；
