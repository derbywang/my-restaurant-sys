# 顾客自助点餐：规格和加料的选择对话框（设计，2026-11-15）

状态：设计，等确认后实现（先写测试）。范围：顾客页面（手机、平板；立式机 / 横屏机共用同一个组件和购物车）。关联：`data-pack.md`（模板和导入）、`jp-tax-design.md`（税）、`self-order-design.md`。

## 1. 现状和问题

- 规格（`POS Item Variants`）和加料（`Item Add On`）都是**另一个有独立价格的商品**（子表只有一个链接字段），店员端（收银台、服务员）的 `ProductDialog` 已经支持。
- 顾客页面**没有**：点一下卡片直接加 1 份（`MenuGrid`、`MobileQRLayout`），购物车一个商品一行（`lib/cart.ts`）。服务器的 `get_customer_product` 已能返回规格和加料（名称已按语言翻译），但页面没调用，且返回的 `rate` 是空的。
- 顾客只能点「セルフオーダー可」的菜（`_clean_items` 检查）。加料商品要对顾客隐藏（不是独立的一张卡片），所以**服务器要放行"属于某道菜的规格和加料"**。

## 2. 对话框

### 2.1 什么时候弹出
- 顾客点一道**有规格或加料**的菜的卡片，弹出对话框。**没有规格和加料的菜保持现在的一键加入**。
- 菜单接口给每张卡片带 `has_options`，页面据此决定。

### 2.2 内容（从上到下）
1. 图片（`show_item_images` 为开时）、菜名、说明（`show_item_descriptions` 为开时）。
2. **规格**（有规格时）：单选按钮，一行一个，写规格名和**含税单价**。例：「にぎり（並） ¥1,100」「にぎり（上） ¥1,650」「にぎり（特上） ¥2,200」。默认选中被点的那一张卡片（基本品）。
3. **加料**（有加料时）：复选框，一行一个，写加料名和**加价（含税）**。例：「☐ 大盛り　＋¥110」。名称显示时去掉前面的「菜名・」（加料商品的完整名称是「まぐろ丼・大盛り」，对话框里菜名已经在上面，所以只显示「大盛り」；没有这个前缀就显示完整名称）。
4. **数量**：− 数量 +。
5. **备注**（`item_notes_enabled` 为开时）：和现在的购物车备注一样。
6. **小计（含税）**：（规格价 + 勾选的加料价）× 数量，随选择实时变化。
7. 按钮：「カートに入れる」和「閉じる」。

### 2.3 含税价
- 全部由**服务器**算（`prices_incl_tax`，和菜单一样，按堂食 / 外带的税率）：规格、加料各自的含税单价。页面不算税，价格不含税的数字不发给页面（现有规则）。
- 加料的税率跟着它自己的种类（导入时默认等于主菜的种类）：外带时食品的加料是 8%，酒类的加料是 10%。
- 购物车合计仍然用 `preview_customer_cart`（服务器算，含折扣和切舍规则）。

### 2.4 网格上的规格卡片
- 一组规格（基本品和它的规格）在网格里**只显示一张卡片**（基本品，即菜单里排在最前面的那个），价格写成「¥1,100〜」（组里最低的含税价）。其余规格只在对话框里。
- 加料商品不出现在网格里。
- 判断规则（服务器）：组 = 通过 `POS Item Variants` 链接（任一方向）连起来的商品；组里菜单顺序最靠前的是基本品。

## 3. 购物车

### 3.1 一行 = 一个"组合"
- 一行的内容：**主菜（规格已定）+ 加料列表 + 数量 + 备注**。键 = 主菜 + 排序后的加料。同样的组合再加一次就加数量；不同组合（例如有 / 没有大盛り）是不同的行。
- 显示：第一行「にぎり（上） × 2　¥3,300」，下面缩进几行「＋大盛り　¥220」。**主菜和加料显示在一起**。
- 数量 −/+ 作用于整个组合：**加料的数量总是等于主菜的数量**（加料不单独加减）。要去掉加料就删掉这一行、重新选。
- 购物车保存在浏览器里（`lib/cart-store.ts`）：版本升级，读到旧格式的购物车就丢弃，不报错。

### 3.2 提交
- 发给服务器的还是**平铺的行**（`add_customer_items` 的 `items`）：主菜一行 {item, qty, comment}，每个加料一行 {item, qty = 主菜数量}，主菜和它的加料**紧挨着**。服务器不信任页面的任何金额，仍然按 Item Price 重新计价。
- `preview_customer_cart` 同样用平铺的行。

### 3.3 已点内容
- 「ここまでのご注文」仍然显示服务器返回的订单行（`mergeOrderLines`：同一商品 + 同一备注合并）。加料商品的名称是「主菜名・加料名」，所以显示成「まぐろ丼・大盛り × 2 ¥220」，看得出属于哪道菜。**这里不做成组显示**（见第 6 节）。

## 4. 多语言
- 规格名、加料名来自各自商品的翻译（`custom_translations`），按顾客的语言（`item_names`）。导入器按「主菜译名・加料译名」自动拼出加料的译名。
- 对话框和购物车的文字走现有的 i18n（ja / zh / ko / en 四份语言文件），新增的键四种语言同步。
- 没有译名就显示日语名（和菜名一样）。

## 5. 年龄确认（酒类）
- 规格或加料里有需要问年龄的商品（`age_check`，按商品所属的种类分类）时：在顾客按「カートに入れる」时，**和现在一样先弹「20歳以上ですか？」**（`AgeConfirmDialog`），回答「はい」才加入购物车；回答过一次后本次点餐不再问（服务器也记着）。
- 服务器端不变：`add_customer_items` 对**所有行**（包括加料）检查 `_age_checked_items`，没有回答「はい」的会话不能下单。

## 6. 要不要一起做：主菜和加料成组显示、数量联动（建议）

**成组显示**（厨房单、小票、订单详情把加料缩进显示在主菜下面）：
- 要在每一行记录"属于哪个组合"（`POS Invoice Item` 和 `URY KOT Items` 各加一个字段，例如 `custom_option_group`），还要改：厨房屏幕（mosaic）和厨房单打印、小票模板和 `receipt.py`、订单详情和合并同菜行的规则、收银台和服务员的购物车 / 拆单 / 合算，以及顾客页面的已点内容。每个地方都要测试，小票和厨房单还要实物确认。**约 3～4 天**。
- **建议开店前不做**：加料商品的名字是「主菜名・加料名」，厨房单、小票、订单详情上一眼就知道属于哪道菜，加料行紧挨着主菜行。成组显示是美观和防错的改进，不是必要。

**数量联动**：
- 顾客页面：**在对话框的设计里已经包含**（购物车一行 = 主菜 + 加料，数量一起变；提交时加料数量 = 主菜数量），不需要额外做。
- 收银台和服务员（已发送的订单）：改主菜数量时加料行不变。要联动就需要上面的"组合"字段，**约 1～2 天**；单做收银台购物车里**未发送**的联动（只在前端，不保存）约 0.5 天，但已发送的订单仍然不联动，价值有限。
- **建议**：开店前不做；培训要点里写「改了主菜数量，要同时检查加料行」；开店后观察实际出错的频率，再决定做不做成组显示和联动。

## 8. 不做的（这一版）
- 加料的数量和主菜不同（例如「大盛り 只要 1 份」而主菜 2 份）；规格和加料的必选 / 最多选几个这类限制；加料之间的互斥。需要时再加。
- 成组显示和已发送订单的数量联动（第 6 节）。
