### 2.5 排练站点和正式站点：二维码、平板、切换（2026-11-08 补）

**桌上二维码里是什么**（读 `self_ordering.py` 的 `generate_qr_token` / `_verify_qr_token`、`qr_print.py`）：一个网址 `<public_url>/order/?t=<令牌>`，令牌是 base64(`<Self Ordering Profile 的名字>|<桌子名>|<HMAC-SHA256(前两项, qr_signing_secret)>`)。**没有任何东西存在服务器的每张桌子上**（无状态）。所以二维码只依赖四样东西：① 网址里的域名；② Profile 的名字（现在是分店名 `三友寿司`）；③ 桌子名；④ Profile 的 `qr_signing_secret`。这四样在排练站点和正式站点上**一模一样**，二维码就两边都有效，贴一次就够。

**怎么保证一模一样：**
1. **签名密钥用一个约定的值**，不让每个站点自己随机生成（现在 Profile 保存时为空就自动随机生成）。12/1 定下这个值，存进密码管理器，数据包里带它；`deploy_check` 加一项：用样例令牌验证签名。
2. **域名**：二维码用正式域名（11/15 定）。试营业期间域名指向排练站点，切换（12/19）时指向正式站点，**贴出去的二维码不变**。
3. **Profile 名和桌子名在 11/27 冻结**，之后不再改（改了，对应的二维码全部作废，要重新打印）。**排进日历**：11/27 冻结，12/4 打印，12/9～12/11 贴。
4. **换密钥会让所有已贴二维码失效**（这也是紧急时的一个开关，比如二维码被人拍下乱传），要重新打印。

**平板：** 设备记录（`URY Ordering Device`）里存的是 `device_id` 和**凭据的哈希**，平板的 localStorage 里是原始凭据。数据包把设备记录（含哈希，不含原始凭据）一起带到正式站点，平板就**不用重新登记**。平板访问店里的固定局域网名字（`ury.lan`），切换时这个名字也指向正式站点。（要做：数据包里"导出 / 导入设备"。）

**切换站点：** 排练站点和正式站点在同一台服务器上，用同一套脚本建，数据包可重复执行（幂等）。切换 = 让域名和 `ury.lan` 从排练站点改指向正式站点（frappe_docker 里用 `FRAPPE_SITE_NAME_HEADER` 之类的单点设置，**具体机制 12/1～12/4 的部署演练里验证**，这里先当作一个已知风险）。正式站点在 12/10～12/11 就建好，期间不对外：没有开班记录，顾客扫码只会看到"未开放"，平板显示等待画面，所以不会产生单据。

**12/19 切换后的验证（不产生单据）：** 手机扫一张贴好的二维码 → 看到"未开放"；一台平板 → 等待画面；各角色账号能登录；厨房屏幕账号能登录；QZ 打印一张测试页（不是小票）；`deploy_check` 结果为空；备份能跑；Error Log 干净。**12/20 开班后的第一单是真正的第一单**。

**数据包里不带的：** 单据（POS Invoice、KOT、订单号）、开班记录、会话；这些在正式站点上从零开始，账本是干净的。

**风险：** ① 切换机制没验证过（12/1 演练）；② 试营业中改了菜单或桌子，要在 12/18 再应用一次数据包（桌子名不许改，菜单价格可以改）；③ 排练站点和正式站点同时在一台服务器上，要看内存和磁盘够不够。

## 3. 平板需要你准备的（先回答这些）

## 5. C 的 5、6、7、9 是什么（设计 5.1，开工时我再读代码核对现状）

## 6. 风险

1. **硬件到货**：平板、服务器、打印机和钱箱的到货日期是最大的不确定因素；缓冲主要为它们留着。
2. **实机验证往返**：每项要你验证，建议每周固定一两个时段集中验证，而不是随时。
3. **翻译**（2.4）：要不要在开店时就有中文 / 韩文切换，需要你决定。
4. **试营业用的排练站点**：需要服务器资源（磁盘、内存）能同时跑两个站点；12/1 的部署演练会验证。
