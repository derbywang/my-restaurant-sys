# 数据包（Data pack）设计

状态：设计 2026-11-15，模板和读取器已做，导入器（plan / apply）按下面的顺序做。相关：`launch-plan.md` 2.2、2.5（二维码和平板）、2.6（机密）。

## 1. 目的和范围

- 排练站点和正式站点（12/10～12/11 建）要有**一样的**桌子、菜单、账号、设备、设置，而且要**能重复执行**（试营业中改了菜单，12/18 再应用一次）。
- **做成通用的，不为三友寿司写死**（2026-11-15 要求）：将来卖给其他料理店，那些店要把现有的数据搬进来。所以 Excel 是一套"标准导入格式"，分店名、Profile 名、分类、厨房、房间名全部从表里读。
- 设置向导继续负责「只做一次」的部分：公司、分店、餐厅、税、会计年度、支付方式。数据包在向导之后执行，从表里读到分店名后**核对它已存在**，不存在就报错并提示先走向导，不替向导建。

## 2. 包里有什么

| 内容 | 来源 | 格式 |
|---|---|---|
| 店舗（分店名、餐厅名、菜单名、Self Ordering Profile 名） | 店主填 | Excel |
| 房间、桌子 | 店主填 | Excel |
| 厨房（生产单位） | 店主填 | Excel |
| 菜品分类（URY Menu Course，含提供顺序和中韩英名称） | 店主填 | Excel |
| 菜单（品名、分类、种类、厨房、税抜价、自助点餐、推荐、停售、中韩英名称、图片文件名） | 店主填 | Excel |
| 店员账号（姓名、登录 ID、角色、语言） | 店主填 | Excel |
| 顾客（移行用，可选） | 店主填 | Excel |
| 桌上平板的设备记录（含凭据哈希，不含原始凭据） | 从排练站点导出 | JSON |
| Self Ordering Profile 的设置（`public_url` 等，不含签名密钥）、站点设置 | 我 | JSON |

**不带**：单据（POS Invoice、KOT、订单号）、开班和交班记录、会话、二维码签名密钥（2.6）、账号密码、`encryption_key`、会计期初余额。

## 3. 标准导入格式（Excel）

文件：`docs/data-pack/店舗データ記入表_v1.xlsx`（日语，每个店都能直接用）。由 `ury/setup/datapack/template.py` 生成：

    cd /workspace/development/frappe-bench
    env/bin/python -c "from ury.setup.datapack.template import build_template; build_template('apps/ury/docs/data-pack/店舗データ記入表_v1.xlsx')"

**表头和列只在一个地方定义**：`ury/setup/datapack/schema.py`。模板、读取器（`reader.py`）和以后的导入器都按它走，不会出现"模板写的和导入器要的不一样"。改格式 = 改 `schema.py`、升 `FORMAT_VERSION`、重新生成文件；测试 `ury.setup.test_datapack_template`。

**每个工作表的布局**：第 1 行是标题和说明，第 2 行是表头（带 `*` 的是必填），第 3 行是填写方法，第 4 行是示例，**第 5 行起才是数据**；第 3、4 行不要删。第一个工作表「説明」是说明页（填写顺序、规则、种类和税率、价格怎么写、多语言和图片、不能改的名字、密码、导入流程、不包含的内容）。

**读取器**（`read_pack`）一次返回所有问题，写成给填表人的句子（工作表、第几行、哪一项、什么问题）：缺工作表、表头被改、必填项为空、不是整数、○× 以外的符号、种类不是三种之一、同一个名字用了两次、指向别的工作表的名字（分类、厨房、房间）在那个工作表里不存在、邮箱格式。**它不写任何东西。**

### 价格：填税抜价

系统的价格规则是**税抜价**（`jp-tax-design.md`：不含税价相同，堂食和外带的含税价不同；每张账单每个税率只算一次税额）。所以模板的价格列是**税抜价格**；右边的「税込・店内」「税込・持ち帰り」是**公式列**（确认用，导入器不读）。注意：
- 店里的菜单如果是**税込价**，要先换算：税込 ÷ 1.1（例：税込 1,100 → 1000）。
- 税込价是整数（例如 ¥1,000）时，税抜价是 909.09，**不能写成整数**，读取器会报错。这是业务问题（价格规则是否改成税込，或者定价改成"税抜整数"），要和税理士商量，**不是读取器能决定的**。
- 逐品把税込加起来，和账单合计可能差几日元（账单按税率合计后只算一次税额）。

### 种类和厨房

**种类（食品 / 酒类 / 非食品）**决定税率，并复用设置向导的规则（`ury/setup/jp_tax.py` 的 `menu_group_for_kind`）：食品店内 10%、外带 8%，酒类和非食品都是 10%；酒类还会在自助点餐里问年龄。**厨房**对应 URY Production Unit，按 Item Group 路由（生产单位的 `item_groups`）。导入器的做法（待做时再确认）：每个（种类，厨房）一个叶子分类，挂在种类的父分类下（税率由父分类决定），再把它加进厨房的 `item_groups`。

## 4. 命令（要做）

    bench --site <站点> execute ury.setup.datapack.plan   --kwargs '{"folder": "<目录>"}'   # 只读：会新建 / 更新 / 不变的列表，以及"表里没有的"
    bench --site <站点> execute ury.setup.datapack.apply  --kwargs '{"folder": "<目录>"}'   # 先备份，确认后写入
    bench --site <站点> execute ury.setup.datapack.export --kwargs '{"folder": "<目录>"}'   # 从排练站点导出设备等

目录里有 Excel 文件、`images/`（可选）、JSON。`plan` 不写数据（不是"先执行再回滚"）。`apply` 之前先 `bench backup`，并按"改站点数据要先列清单"的规则让店主确认。

## 5. 规则

- **幂等**：按自然名字（桌子名、菜名、账号）查找，存在就更新"包里写了的字段"，不存在就新建；第二次执行结果是"全部不变"。
- **只增不删**：站点上多出来的东西不删，在 `plan` 里列为"表里没有的"。
- **名字不改**：桌子名、Profile 名在包里变了，报错而不是改名（二维码依赖它们，2.5）。
- **出错就停**，写明哪一行哪一项；做完自动跑 `deploy_check`。
- **数据文件不进 git**（有账号名单和设备哈希，按机密处理）；脚本在 git 里，git 里放一套示例数据给测试用。
- 站点设置显式设置：`language = ja`、`time_zone = Asia/Tokyo`、`country = Japan`、`default_currency = JPY`（2.5）。

## 6. 账号和初始密码

- 表里**不写密码**。导入器给每个账号生成一次性初始密码（随机，每人不同），写进服务器上**只有店主能读**的文件（权限 600，不进 git，不进备份之外的地方），店主发给店员。
- 店员（Website User，没有 Desk）**第一次登录后自己改密码**：`/update-password`（需要旧密码），`/me` 页有入口（`report-permissions.md` 已实测）；步骤写进 `staff-training-points.md`。
- **"首次登录强制改密码"的评估**：Frappe 没有"第一次登录就强制"的开关，只有 System Settings 的 `force_user_to_reset_password`（"N 天没改密码就要在登录时改"，全站统一）和用户的 `last_password_reset_date`（`frappe/auth.py` 的 `force_user_to_reset_password`）。做法：数据包创建账号后把 `last_password_reset_date` 设成很早的日期，并把 `force_user_to_reset_password` 设成一个大的天数（例如 365）。结果：每个新账号第一次登录会被带到改密码页，改完之后一年内不再被要求（以后每年改一次，附带效果）。注意：① 账号创建时 Frappe 会把 `last_password_reset_date` 设成今天，所以要在设初始密码**之后**再改；② 影响所有人（店主和已有账号一年后都会被要求改密码，Administrator 等标准账号除外）；③ 要用真实登录（HTTP）测试 Website User 的流程。**结论：值得做，约 0.25 天，放在账号那一步，做之前再确认。**

## 7. 其他店的数据迁移（2026-11-15）

三友寿司是新店，这次不迁移；将来卖给已经在用别的收银系统（Airレジ、スマレジ、Square 等）的店，要把现有数据搬进来。

**迁移的**（填进标准导入格式的 Excel）：

| 数据 | 对应的工作表 | 说明 |
|---|---|---|
| 菜单（品名、价格） | メニュー | 价格要统一成税抜；旧系统导出的多半是税込，要换算 |
| 分类 | 分類 | 旧系统的"部门 / 类别" |
| 税率（种类） | メニュー的「種類」 | 旧系统的轻减税率标记 → 食品；酒类要按旧系统的类别判断，**要人工确认** |
| 桌子和房间 | テーブル、ルーム | 旧系统有桌位的话 |
| 店员 | スタッフ | 只迁姓名和角色，密码重新发 |
| 常客资料 | 顧客（移行用） | 姓名、电话、邮箱、备注 |
| 厨房分配 | 厨房 | 每道菜送到哪个厨房 |

**不迁移的**：
- **过去的销售记录、账单、交班记录**：留在旧系统，或从旧系统导出来保存，不导入新系统。理由：新系统的账本是从开业日起算的，导入历史单据会和税额计算、交班、小票号码混在一起，而且无法保证旧单据的税额按我们的规则重算。
- **法定保存期限**：账簿和交易凭证要保存，期限大致是法人 7 年（用欠损金结转的年度最长 10 年）、个体经营者的账簿通常 5～7 年，电子交易数据有电子帳簿保存法的要求。**具体年限和保存方式以税理士和国税厅的说明为准**，旧系统合同到期前要先把数据导出来（CSV / PDF）存好，不能因为换系统把凭证弄没了。
- 库存数量、成本、员工考勤等：本系统不迁移（餐厅的库存和成本另说）。

**会计期初余额**：走 ERPNext 的标准方式（开始日的 Journal Entry / Opening Entry，或会计软件导入），**不放进数据包**。这是会计师的工作，要有开业日的试算表。

**换系统的流程建议**：① 在旧系统里导出全部可导出的数据（商品、顾客、历史销售），存档；② 填标准导入格式；③ `plan` 看结果；④ 在测试站点上演练，店员实际点一遍；⑤ 选一个非营业日切换；⑥ 旧系统在保存期限内留着只读或存导出文件。

## 8. 开发顺序

1. 模板和读取器（**已做** 2026-11-15）。
2. 菜单导入（含分类、厨房、中韩英名称、可选图片；重复导入不产生重复）。
3. 房间和桌子。
4. 账号（初始密码文件、语言、分店用户表、POS Profile 适用用户；强制改密码）。
5. Self Ordering Profile 和设备（导出 / 导入，不含密钥）。
6. 站点设置和 `plan` / `apply` 的外壳。

每一步先写测试（红 → 绿），会写数据的测试先在临时站点上跑，结果干净再上 `ury-test.localhost`；`apply` 的集成测试用示例数据，在事务内跑。
